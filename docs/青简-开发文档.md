## 1. 项目定位与愿景

| 维度 | 说明 |
| --- | --- |
| **名称** | 青简（QingJian） |
| **一句话定位** | 轻量、现代、开源、本地优先的个人信息工作台，并原生支持 AI 能力 |
| **核心理念** | 数据归用户自己所有（本地优先），界面现代顺手，能力可被 AI 增强，代码完全开源可审计 |
| **首期形态** | Web 端（兼容 Tauri 桌面窗口与移动端视图），后续一键打包为 exe（Windows）与 apk（Android） |
| **目标用户** | 注重隐私与效率的个人用户：开发者、研究者、知识工作者、学生 |

**关键词解释**
- **轻量**：安装包小（目标桌面端 < 15MB）、启动快、依赖少。
- **现代**：组合式 UI、暗/亮色主题、快捷键优先、流畅交互。
- **开源**：代码托管 GitHub，明确 License，可自托管、可审计。
- **本地优先（Local-First）**：数据默认存本地，离线可用，云端为可选项而非必须。
- **AI 支持**：内置统一 AI 接口，既可接云端大模型 API，也可接本机运行的本地模型（如 Ollama）。

## 3. 技术栈详解

### 3.1 前端（Vue 3 + Vite）
- 使用 `<script setup>` 组合式语法，TypeScript 全程开启。
- UnoCSS 预设 `presetUno` + `presetIcons`，图标用 `iconify`。
- 主题系统：基于 CSS 变量定义设计令牌（颜色、间距、圆角），支持暗/亮色与跟随系统。
- 快捷键优先：全局命令面板（⌘K / Ctrl+K），所有核心操作可键盘到达。
- 离线可用：PWA 可选（service worker 缓存），首期以 Tauri 壳为主。

### 3.2 打包（Tauri v2）
- Tauri v2 单一前端代码库，通过 `src-tauri` 中的 Rust 工程承载原生能力。
- 桌面目标：`windows`（msi/exe）、`linux`、`macos`。
- 移动目标：`android`（apk/aab）。移动端需注意权限与存储路径差异（用 Tauri 路径 API 统一）。
- 窗口配置：无边框/自定义标题栏可选，最小宽度约束，系统托盘常驻（可选）。

### 3.3 本地存储（本地优先）
- **生产（Tauri）**：`@tauri-apps/plugin-sql` 操作本地 SQLite 文件，数据库文件存于用户数据目录，可整体复制备份。
- **Web 预览**：Dexie 实现相同 Repository 接口，便于没有 Rust 环境时也能开发 UI。
- 抽象层 `StorageAdapter`：上层业务只依赖接口，不关心底层是 SQLite 还是 IndexedDB。

> 注：知识库模块在上述结构化存储之外，另支持 **Vault 文件模式**（见 5.3），直接以 Markdown 文件为数据源，用于对接 Obsidian。

### 3.4 AI 能力（双通道）
- 统一 `AIProvider` 接口，业务层只调用 `chat()`，不感知云端/本地。
- 云端请求经 Tauri 后端转发（Rust 用 `reqwest` 发 HTTPS），**API Key 仅存本地配置，不进前端包体**。
- 本地模型经 Tauri 调用本机 Ollama（`http://127.0.0.1:11434`），完全离线。
- 支持流式输出（SSE / AsyncIterator），打字机效果。

## 4. 系统架构

```
┌─────────────────────────────────────────────┐
│               前端 (Vue 3 + Vite)             │
│  UI 组件层 → Pinia 状态 → Repository 数据层    │
│  AI 服务层 (AIProvider 抽象)                  │
└───────────────┬───────────────────┬──────────┘
                │ Tauri invoke      │ HTTP(S)
                ▼                   ▼
┌──────────────────────┐   ┌────────────────────────┐
│  Tauri (Rust) 后端    │   │  外部 AI 服务            │
│  - SQLite 存储        │   │  - 云端：OpenAI兼容API   │
│  - 文件系统/路径      │   │  - 本地：Ollama(本机)    │
│  - AI 请求中转(安全)  │   └────────────────────────┘
└──────────────────────┘
         │
         ▼
┌──────────────────────┐
│  本地数据目录          │
│  qingjian.db (SQLite) │
│  附件 / 配置 / 缓存    │
└──────────────────────┘
```

**分层职责**
1. **UI 层**：页面与组件，只做展示与交互。
2. **状态层（Pinia）**：跨组件共享状态。
3. **数据层（Repository）**：通过 `StorageAdapter` 读写，屏蔽存储差异。
4. **服务层（AI/文件/设置）**：业务能力封装。
5. **原生层（Tauri）**：真正落盘与网络中转。

### 5.3 Obsidian 兼容（知识库关键能力）
Obsidian 的 Vault 本质是**本地 Markdown 文件 + `.obsidian` 配置目录**，数据格式完全开放（`.md` 文本、YAML frontmatter、`[[wikilinks]]`、`#标签`），不存在私有锁定，因此青简可在「知识库」模块直接对接。

**推荐集成方式：Vault 直连模式**
- 知识库支持两种数据源：
  - 内置库（默认）：SQLite/IndexedDB，独立存放，适合不想依赖 Obsidian 的用户。
  - Vault 模式：在设置中选择 Obsidian Vault 文件夹，青简直接读写其中的 `.md` 文件，成为 Obsidian 的「另一个前端」。
- 双向可用：青简里编辑的笔记，回到 Obsidian 打开完全一致；反之亦然（青简需监听文件变化以热更新）。

**必须兼容的 Obsidian 特性**
| 特性 | 说明 | 青简处理 |
| --- | --- | --- |
| Markdown 正文 | 标准 CommonMark | 原生支持 |
| `[[双链]]` / `[[笔记\|别名]]` | 内部链接 | 编辑器渲染 + 点击跳转；建立反链（backlinks）与关系图谱 |
| `#标签` / frontmatter `tags` | 分类 | 解析为标签索引 |
| YAML frontmatter | `title/aliases/created/updated` 等 | 读写并映射为元数据 |
| 附件 `![[image.png]]` | 嵌入资源 | 指向 Vault 附件目录 |
| Obsidian URI | `obsidian://open?vault=名称&file=路径` | 提供「在 Obsidian 中打开」入口，双向跳转 |

**进阶（可选）**：反向链接面板、标签视图、图谱视图（基于 wikilink 解析构建）；同步遵循「文件即真相」，冲突以最后写入 + 版本标记处理，不做破坏性合并。

**已确认方案**：采用 **Vault 直连模式**（2026-07-29 确认），纳入 V1 迭代。实现要点：
- 设置中让用户选择 Vault 文件夹路径（Tauri 路径 API 取绝对路径）。
- 知识库 Repository 新增 `VaultSource` 实现：读目录树、读写 `.md`、解析 frontmatter 与 `[[wikilinks]]`。
- 通过文件系统监听（Tauri `fs` watch / `notify`）实现外部变更热更新，避免与 Obsidian 同时编辑时数据陈旧。
- 内置库与 Vault 模式互斥切换；首次进入提示用户选择数据源。
- 索引层：启动时扫描 Vault 构建内存索引（标题/标签/链接），支撑全文搜索与反链，不改动原始文件结构。

> 原则：**MVP 所有功能均不依赖云端即可完整使用**；云端/同步始终是增强项，而非前置条件。

## 6. 数据模型与本地存储（草案）

以 SQLite 为例（Web 端 Dexie 结构对齐）：

```sql
-- 笔记
CREATE TABLE notes (
  id TEXT PRIMARY KEY,
  title TEXT,
  content TEXT,        -- Markdown
  parent_id TEXT,      -- 目录树
  tags TEXT,           -- JSON 数组
  created_at INTEGER,
  updated_at INTEGER
);

-- 待办
CREATE TABLE todos (
  id TEXT PRIMARY KEY,
  title TEXT,
  done INTEGER DEFAULT 0,
  priority INTEGER,
  due_date INTEGER,
  note_id TEXT          -- 可关联笔记
);

-- AI 对话
CREATE TABLE chat_sessions (
  id TEXT PRIMARY KEY,
  title TEXT,
  provider TEXT,       -- cloud / local
  model TEXT,
  created_at INTEGER
);
CREATE TABLE chat_messages (
  id TEXT PRIMARY KEY,
  session_id TEXT,
  role TEXT,
  content TEXT,
  created_at INTEGER
);

-- 设置（含加密后的 AI Key）
CREATE TABLE settings (
  key TEXT PRIMARY KEY,
  value TEXT
);
```

**存储要点**
- 主键统一用 UUID（或 `crypto.randomUUID()`）。
- 时间用 Unix 毫秒。
- AI Key 在写入 `settings` 前于本地做加密（对称加密，口令来自用户主密码或系统密钥链），严禁明文落库。

## 7. AI 能力设计

### 7.1 统一接口（前端 TS 草案）
```ts
export type ChatRole = 'system' | 'user' | 'assistant'
export interface ChatMessage { role: ChatRole; content: string }

export interface AIChatOptions {
  model?: string
  stream?: boolean
  signal?: AbortSignal
}

export interface AIProvider {
  id: string
  name: string
  type: 'cloud' | 'local'
  chat(messages: ChatMessage[], opts?: AIChatOptions): Promise<AsyncIterable<string> | string>
  listModels(): Promise<string[]>
}
```

### 7.2 两种实现
- **CloudProvider**：向 Tauri 后端 `invoke('ai_proxy', {...})` 发请求，后端用 `reqwest` 转发到配置的云端 endpoint（OpenAI 兼容）。
- **LocalProvider**：向 Tauri 后端 `invoke('ai_local', {...})`，后端转本机 Ollama。用户无本机模型时自动提示安装。

### 7.3 配置与安全
- 用户在「设置」中填写云端 API Key，存于本地加密。
- 后端中转时读取本地配置，Key 永不进入前端产物。
- 本地模型默认 `http://127.0.0.1:11434`，可配置。

## 10. 开源与 GitHub 工程规范

### 10.1 License
- **推荐 MIT**（最宽松、最友好，鼓励采用与衍生）。
- 若希望任何 SaaS 衍生也必须开源，可改用 **AGPL-3.0**。
- 个人开源工具通常选 MIT；请在 README 明确。

### 10.2 分支与版本模型（轻量 Trunk-Based）
- `main`：受保护，始终可发布。
- `feature/*`：短生命周期功能分支，完成后提 PR 合并。
- 版本号遵循 **SemVer**（如 `v0.1.0`）。
- 打 `v*` tag 即触发 Release 自动构建（见 10.4）。

### 10.3 必含仓库文件
- `README.md`：项目介绍、特性、截图、快速开始、构建说明、路线图、License。
- `CONTRIBUTING.md`：如何提 Issue/PR、开发环境搭建、代码规范。
- `SECURITY.md`：安全漏洞反馈渠道（尤其涉及本地密钥/加密）。
- `LICENSE`：许可证全文。
- `.gitignore`：忽略 `node_modules`、`src-tauri/target`、本地数据库、密钥文件。

### 10.4 CI/CD（GitHub Actions）
- **前端 CI**：`npm ci` → `lint` → `vitest` → `vite build`。
- **Release 构建**：使用 `tauri-apps/tauri-action`：
  - Windows runner → 产出 `.msi`/`.exe`。
  - Ubuntu runner + Android 环境 → 产出 `.apk`。
- 每次打 `v*` tag 自动创建 GitHub Release 并上传对应安装包。

### 10.5 提交规范
- 采用 Conventional Commits（`feat:`、`fix:`、`docs:`、`chore:`…），便于自动生成 changelog。

### 10.6 发布前安全清单（上传 GitHub 前必做）
**A. 密钥与凭证（最高优先级）**
- `.gitignore` 必须忽略：`.env`、`.env.*`（除 `.env.example`）、`*.db`/`qingjian.db`、用户数据目录、`src-tauri/target/`、`src-tauri/gen/`（生成物）、任何 `*.keystore`/`*.p12`/密钥文件。
- 提供 `.env.example` 仅含占位符；真实 AI Key 由用户本地填写，经 Tauri 后端中转、本地加密，**绝不进前端包体，也不进仓库**。
- 提交前扫描历史是否误含密钥：`git log -p | grep -iE 'api_key|secret|token|password'`，或接入 `gitleaks` / `trufflehog` 作为本地/CI 预提交钩子。
- 若已误提交密钥：立即在服务商处吊销，并用 `git filter-repo` 清理历史后强制推送；不要指望「删掉再提交」能消除历史记录。

**B. 用户数据与隐私（本地优先核心）**
- 仓库只含代码与文档，**绝不提交任何真实用户数据**（笔记、Vault 内容、密码库）。
- 若需演示素材，使用明显虚构/脱敏的样例数据。
- Vault 直连：配置只存 Vault 文件夹路径（在本地数据库，已被 `.gitignore` 排除），不要示例里带用户名等隐私。
- 密码保险箱：加密口令来自用户主密码/系统密钥链派生，绝不写死；加密实现须经审查，禁止明文落库。

**C. 依赖与供应链**
- 提交 `package-lock.json` 与 `Cargo.lock` 以锁定版本。
- 启用 GitHub **Dependabot**、**Secret Scanning**、**CodeQL**（仓库 Settings → Security 开启，或加 `.github/dependabot.yml` 与 CodeQL workflow）。
- 发布前跑 `npm audit`（前端）与 `cargo audit`（Rust）；不引入来源不明的包。

**D. Tauri 权限最小化（capabilities）**
- 仅授予业务必需的 API：`dialog`、`fs`（限定目录）、`sql`、`http`（如需云端 AI 中转，限定域名或仅本机）、`updater` 等按需开启。
- 避免 `fs` 全量可读写、`http` 任意域名，防止恶意内容借本地应用越权访问文件/内网。
- 校验用户自定义 AI endpoint，防 SSRF（限制为本机或白名单域名）。

**E. 构建与签名**
- Windows 代码签名（Authenticode）与 Android `keystore`/上传密钥**只存 GitHub Actions Secrets**，绝不入库。
- Tauri 签名相关变量走 CI 环境变量；`tauri.conf.json` 不写明文密钥。
- 启用仓库 2FA、main 分支保护（禁直接 push，需 PR + review）。

**F. 合规**
- 确认依赖许可证与 MIT 兼容；不夹带未授权图标/字体（商用字体需替换或注明授权）。
- `SECURITY.md` 提供漏洞反馈渠道，鼓励负责任披露。

## 11. 关键风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Tauri 移动端（apk）配置复杂 | 出包受阻 | M5 再攻坚，先确保桌面 exe 稳定；参考官方 android 模板 |
| AI Key 安全 | 密钥泄露 | 仅后端中转、本地加密、绝不进前端包 |
| Web 与 Tauri 存储差异 | 开发/生产不一致 | 统一 `StorageAdapter` 接口，schema 对齐 |
| 本地模型体积大 | 用户门槛 | 默认云端可跑，本地为可选增强，安装时引导 |
| 功能膨胀背离「轻量」 | 包体增大 | MVP 严控范围，插件化延后非核心功能 |
